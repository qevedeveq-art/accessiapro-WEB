RAG interne sécurisé en PME : indexer sans exfiltrer

Un RAG interne — Retrieval Augmented Generation — permet à un assistant IA de répondre à partir de documents propres à l'entreprise sans envoyer ces documents à un tiers. C'est l'architecture la plus demandée en PME, et l'une de celles où la sécurité est la plus mal comprise. Ce dossier expose la chaîne technique, les contrôles à mettre en place, les pièges classiques d'exfiltration et les questions à poser à un prestataire avant de démarrer.

Les cinq étapes d'une chaîne RAG

Une chaîne RAG minimale comporte cinq étapes. Comprendre chaque étape est le préalable à toute évaluation de sécurité : la plupart des incidents documentés se logent dans les transitions, pas dans les composants isolés.

  1. Collecte. Rassembler les documents à indexer depuis leurs sources : partages réseau, gestionnaire électronique de documents, base de connaissances, tickets, contrats.
  2. Segmentation. Découper chaque document en fragments cohérents (paragraphes, sections). C'est le grain auquel l'assistant retrouvera l'information.
  3. Vectorisation. Passer chaque fragment dans un modèle d'embedding pour produire une représentation numérique. Ce modèle peut être local ou cloud ; le choix change la surface d'exposition.
  4. Stockage. Écrire les vecteurs et les métadonnées dans une base spécialisée. La base contient l'index, mais surtout les métadonnées (chemin, droits, propriétaire).
  5. Requête. Quand un utilisateur pose une question, le système cherche les fragments pertinents, les concatène au prompt, puis appelle le modèle de génération pour rédiger la réponse.

Contrôles d'accès : la règle qu'on oublie

Le principe de base est simple à énoncer et souvent violé : un utilisateur ne doit pouvoir consulter, via l'assistant, que les documents qu'il aurait pu consulter directement. Cela suppose que la chaîne RAG connaisse l'identité de l'appelant et que la base vectorielle sache filtrer par droits, pas seulement par similarité.

Les implémentations naïves font l'inverse : elles indexent tout, cherchent tout, puis « masquent » ce qui ne convient pas dans la réponse. C'est une politique fragile. Un attaquant, ou simplement un utilisateur curieux, formule une question qui contourne le masquage et récupère une information à laquelle il n'a pas droit. La bonne posture consiste à ne jamais retourner un fragment interdit dès l'étape de recherche.

Journalisation attendue

  • Chaque indexation trace la source, l'auteur, l'horodatage, la version du modèle d'embedding.
  • Chaque requête trace l'appelant, la question, les fragments retournés, la réponse générée.
  • Chaque suppression trace la raison (retrait d'un document, retrait d'un utilisateur, correction d'un droit).
  • Les journaux sont conservés selon la politique interne, séparés des données de production, et accessibles au responsable désigné dans le registre d'usages.

Pièges classiques d'exfiltration

  • Un document piégé dans le corpus qui pousse l'assistant à divulguer d'autres fragments.
  • Une image ou une capture indexée dont le texte OCR contient une consigne cachée.
  • Une base de vecteurs partagée entre utilisateurs sans filtre d'accès en amont.
  • Un modèle d'embedding cloud qui reçoit tout le corpus « pour indexation » sans DPA propre.
  • Un journal de requêtes envoyé au fournisseur du modèle de génération.

Questions à poser à un prestataire RAG

Un prestataire honnête répond à quatre questions sans détour : où sont physiquement stockés le corpus et l'index, quel modèle d'embedding est utilisé et où il s'exécute, comment sont propagés les droits d'accès à chaque étape, quelles traces sont conservées et pour combien de temps. L'absence de réponse claire sur l'une de ces questions est un signal d'arrêt.
